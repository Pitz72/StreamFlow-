# Log tecnico 0.7.3 — Diagnostica attiva (D2) e la vera causa del `-10054`

**Data:** 25 luglio 2026
**Continua da:** [0.7.2](./0.7.2.md)

---

## Il punto di partenza

Dalla 0.7.2 il log finalmente conteneva l'errore. Era questo:

```
✗ connessione persa: [out#0/mp3] Error muxing a packet
                   | [out#0/mp3] Error writing trailer: Error number -10054 occurred
                   | Conversion failed!
```

`-10054` è `WSAECONNRESET`: il peer ha chiuso con un RST. Sembrava un problema di
rete, tanto più che sulla stessa macchina **OBS trasmetteva senza problemi**.

Ipotesi sul tavolo, tutte plausibili e tutte sbagliate: fascia oraria dello streamer
(esclusa da Simone), sorgente concorrente (esclusa, canale libero), antivirus con
scansione HTTP, IPv6 difettoso, banda insufficiente.

## Come si è chiusa

Invece di continuare a ipotizzare, ho provato a **riprodurre** il guasto con una
password volutamente errata contro il server reale.

### Primo tentativo: nessun guasto

```
exit code : 0
httpStatus: null
connected : true
kB        : 79
```

Cinque secondi di `anullsrc` trasmessi senza un errore, **con credenziali fasulle**.
Il che era già di per sé un'informazione: FFmpeg non si accorge di niente.

Il motivo è che senza `-re` FFmpeg spinge l'input generato alla massima velocità —
`speed=52x` nel log. I 5 secondi di audio finiscono nel buffer del socket in un
istante, il processo esce prima che il server abbia modo di far sentire la sua
opinione. **La sonda non riproduceva le condizioni reali.**

### Secondo tentativo, con `-re`: riprodotto

```
Error muxing a packet
Error writing trailer: Error number -10054 occurred
Conversion failed!
size=  8kB time=00:00:00.65
```

Identico al caso in produzione, tempismo compreso. Con una password sbagliata.

### La conferma

FFmpeg non stampa mai uno status HTTP (`httpStatus: null`) perché con
`-chunked_post 0` **non legge la risposta**: manda gli header, scrive il corpo, e
continua a scrivere finché il socket non muore. Il `401` del server esiste, semplicemente
non arriva mai a destinazione.

Verificato con il client HTTP di Node, che invece la risposta la legge:

| Credenziali | Esito |
|---|---|
| `probe-test-user` (inesistente) | `ECONNRESET`, nessuna risposta |
| `PixelDebh_Runtime` + password errata | **`401 Unauthorized`** in 468ms |

Da notare: l'harbor **distingue i due casi**. Un utente sconosciuto viene chiuso senza
risposta; un utente noto con password errata riceve un 401 formale. Il che dice anche
che il nome utente in questione esiste sul server.

Come sottoprodotto: `player.runtimeradio.com` risolve **solo in IPv4** (`159.69.19.75`),
niente record AAAA. L'ipotesi IPv6 è morta per ragioni indipendenti.

## Interventi

### `src/main/streaming/connection-diagnostic.ts` (nuovo)

Sequenza attiva su quattro strati, ognuno annunciato nel pannello Log e scritto su file.

1. **DNS** — `dns.lookup({all, verbatim})`, elenco separato IPv4/IPv6.
2. **TCP** — `net.connect` verso *ciascun* indirizzo, uno alla volta, con i tempi.
   Provare gli indirizzi separatamente è l'unico modo di vedere un percorso IPv6 rotto
   in una configurazione dual-stack.
3. **Credenziali** — `http.request` con lo stesso `PUT` e gli stessi header della
   diretta, ma leggendo la risposta. `401`/`403`/`ECONNRESET` diventano frasi in
   italiano. **Se fallisce, la sequenza si ferma qui**: proseguire produrrebbe solo
   l'errore di rete fuorviante.
4. **Trasmissione** — 20s di `anullsrc` **con `-re`** (senza, non riproduce niente),
   `-loglevel verbose` così l'intero dialogo HTTP finisce nel file.

### `src/main/streaming/ffmpeg-manager.ts`

Il ramo "kicked" introdotto in 0.7.2 ora si sdoppia: caduta entro 3 secondi →
credenziali indicate come causa quasi certa, con la spiegazione del perché FFmpeg
riporti un errore di rete al posto del 401. Oltre i 3 secondi resta la diagnosi
generica (sorgente concorrente, antivirus, intermediario).

### Renderer

`SettingsPanel` — pulsante «Test connessione» accanto a «Apri cartella log»,
disabilitato durante una diretta (la prova occupa il canale).

## Verifica

`tsc` su entrambi i progetti e ESLint sui file toccati: puliti. La logica della sonda
è stata validata contro il server di produzione prima di essere portata nel modulo —
è così che è emerso il problema di `-re`.

---

## Lezione

Due, e vale la pena ricordarle entrambe.

**Un errore di socket non è una diagnosi.** `-10054` descrive cosa ha visto il client,
non cosa ha deciso il server. Quando il client non legge le risposte, l'errore che
riporta è sempre l'ultimo anello della catena, mai il primo.

**Una sonda che non riproduce il guasto non prova niente.** Il primo test è "passato"
e stava per farmi escludere l'ipotesi giusta. Mancava `-re`.
