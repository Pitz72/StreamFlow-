# Runtime StreamFlow v0.1.6 Log

## Data: 2026-03-05
## Versione: 0.1.6 (Grave Fix: Alert UI & Connection Timeout)

### Stato: IMPLEMENTED
Risolti due bug gravi (V3 e V4) identificati nell'audit forense: l'utilizzo di alert nativi bloccanti e la rilevazione inaffidabile dello stato di connessione basata su timeout fisso.

### 🟠 Fix Grave V3: Alert Bloccante

#### Diagnosi
`App.tsx` utilizzava `alert()` nativi del browser per mostrare errori di streaming (es. auth fallita, dispositivo mancante). L'`alert()` in Electron blocca completamente l'Event Loop del Renderer process. In caso di molteplici errori ravvicinati, l'app diventava completamente inutilizzabile e freezata, forzando la terminazione forzata via Task Manager.

#### Soluzione Applicata
1. **Zustand Store (`useStore.ts`)**: Aggiunto uno stato `errorMessage` e un setter corrispondente, escludendoli dalla persistenza.
2. **Toast Component (`App.tsx`)**: Sostituiti tutti i richiami di `alert()` con `setErrorMessage()`. Aggiunto un componente UI in posizionamento assoluto (`fixed bottom-6`) che mostra il messaggio d'errore come un toast visivo non-bloccante.
3. **Auto-dismiss**: Implementato un timer in `App.tsx` che nasconde automaticamente l'errore dopo 5 secondi (`setTimeout`), con adeguato cleanup a dismount.

### 🟠 Fix Grave V4: Timeout Connessione Arbitrario

#### Diagnosi
La determinazione dello stato "Connesso" (`connected`) in `ffmpeg-manager.ts` era basata su un cieco timeout di 2 secondi:
```typescript
setTimeout(() => { if (process alive) sendStatus('connected'); }, 2000);
```
Questo causava una UX fallace: l'interfaccia mostrava "ON AIR" anche se FFmpeg stava bufferizzando localmente, se era in un handshake lento, o se la rete perdeva pacchetti ma FFmpeg non crashava subito.

#### Soluzione Applicata
Aggiornato il parser base dello `stderr` di FFmpeg:
1. Il sistema ora si basa su eventi di progresso reali (`message.includes('size=')` o `message.includes('time=')`). FFmpeg emette questi log *solamente* quando sta effettivamente inviando i frame codificati alla destinazione.
2. I messaggi immediati di rifiuto connessione (`Connection refused`, `401 Unauthorized`, `I/O error`) vengono intercettati per un feedback istantaneo sotto forma di toast error senza aspettare la morte del processo.
3. Il timeout cieco di 2s è stato rimosso in favore di questo event listening reattivo (mantenendo solo un fallback di timeout di 5s molto lasco nel caso in cui stia streamando muto in locale, puramente come fallback).
