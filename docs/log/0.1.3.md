# Runtime StreamFlow v0.1.3 Log

## Data: 2026-03-05
## Versione: 0.1.3 (Critical Fix: IPC Memory Leak)

### Stato: IMPLEMENTED
Risolto memory leak critico nell'IPC listener per lo stato dello streaming. I callback si accumulavano ad ogni re-mount del componente React senza mai essere rimossi.

### 🔴 Fix Critico: Accumulazione infinita di callback IPC

#### Diagnosi
Il componente `App.tsx` registrava un listener per l'evento `STREAM_STATUS` tramite `useEffect`, ma:
1. **Nessuna funzione di cleanup** nel return dell'`useEffect` — React non poteva rimuovere il listener al dismount.
2. **Il preload bridge non esponeva un metodo di unsubscribe** — `ipcRenderer.on()` veniva chiamato senza salvare un riferimento al handler, rendendo impossibile la rimozione successiva.

#### Effetti del bug
- Con React StrictMode (doppio mount in dev), **ogni render** aggiungeva un listener aggiuntivo.
- Ogni evento `STREAM_STATUS` veniva processato da **N callback contemporaneamente** (dove N cresceva nel tempo).
- Risultato: alert duplicati, stato incoerente (`isStreaming` toggleato avanti e indietro), consumo di memoria crescente.

#### Soluzione Applicata

**1. Preload Bridge (`src/preload/index.ts`)**

Refactored il metodo `onStreamStatus` per restituire una funzione di cleanup:

```typescript
// Prima (v0.1.2):
onStreamStatus: (callback) => {
    ipcRenderer.on('STREAM_STATUS', (_event, status, message) => callback(status, message));
    // ❌ Listener anonimo, impossibile da rimuovere
}

// Dopo (v0.1.3):
onStreamStatus: (callback) => {
    const handler = (_event, status, message) => callback(status, message);
    ipcRenderer.on('STREAM_STATUS', handler);
    return () => { ipcRenderer.removeListener('STREAM_STATUS', handler); };
    // ✅ Handler salvato, cleanup restituito
}
```

Punti chiave:
- Il handler è salvato in una variabile `handler` con un riferimento stabile.
- La funzione di cleanup usa `ipcRenderer.removeListener()` con lo stesso riferimento, garantendo la rimozione esatta.

**2. Componente App (`src/renderer/App.tsx`)**

L'`useEffect` ora cattura il valore di ritorno e lo restituisce come cleanup:

```typescript
// Prima (v0.1.2):
useEffect(() => {
    window.electronAPI.onStreamStatus((status, message) => { ... });
    // ❌ Nessun return = nessun cleanup
}, [deps]);

// Dopo (v0.1.3):
useEffect(() => {
    const unsubscribe = window.electronAPI.onStreamStatus((status, message) => { ... });
    return unsubscribe;
    // ✅ React chiama unsubscribe() al dismount = listener rimosso
}, [deps]);
```

### Pulizia aggiuntiva

### Note Tecniche
- Il pattern "return unsubscribe from useEffect" è la best practice React per gestire subscription/listener esterni.
- In React StrictMode (modalità sviluppo), il componente viene montato, smontato e rimontato. Con questo fix, il primo listener viene correttamente rimosso prima che il secondo venga registrato, garantendo un solo listener attivo alla volta.
- Il fix non ha impatto sulle performance: `removeListener` è O(n) dove n = numero di listener per quell'evento (tipicamente 1).
