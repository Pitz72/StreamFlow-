# Runtime StreamFlow v0.2.1-rc Log

## Data: 2026-03-05
## Versione: 0.2.1-rc (Hotfix: Device Mapping Bufferization)

### Stato: IMPLEMENTED
Risolto un bug critico emerso durante il collaudo della prima RC 0.2.0, che si manifestava solo in produzione (o su macchine in cui l'I/O pipe buffer era più frammentato): la tendina dei microfoni risultava vuota costringendo a selezionare il default.

### 🔴 Hotfix CRITICO: Bufferizzazione Stderr `dshow`

#### Diagnosi
Nella release `0.1.8`, il parser per estrarre i nomi dei microfoni nativi in `ffmpeg-manager.ts` intercettava l'evento `stderr.on('data')`. 
Tuttavia, il parsing assumeva erroneamente che l'intero output di FFmpeg (circa 40-50 righe testuali) venisse pushato dalla pipe in un unico grande Event Chunk.
Nella realtà (specialmente sotto `app.asar` in production), il Node Runtime spezza i `Buffer` in molteplici chunk.
Di conseguenza:
1. Una metà di chunk non conteneva la riga header `DirectShow audio devices`, riportando `inAudioSection = false`.
2. O peggio un chunk segava a metà la stringa del device name (`"Microfono (Real...` | `...tek)"`) fallendo le regex.

#### Soluzione Applicata
Abbandonata la strategia di parsing <i>chunk-by-chunk</i>. All'avvio dell'enumerazione, viene istanziata una variabile cache `let outputBuffer = ''`.
Ogni evento di `data` subisce una mera concatenazione `outputBuffer += data.toString()`.
Soltanto all'emissione dell'evento IPC `close` (che certifica the process death di FFmpeg), lo stream testuale viene esploso (`split('\n')`) e il the parser estrae scientificamente le periferiche audio.
