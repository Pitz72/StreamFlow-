## Fix applicati

### V1 — Timer.tsx: `seconds` nelle dipendenze di useEffect
**File:** `src/renderer/components/Timer.tsx`

**Problema:** `seconds` era nelle deps dell'`useEffect` che gestisce il `setInterval`. Poiché `setSeconds(diff)` cambia `seconds` ogni 500ms, l'effect veniva eseguito, pulito (clearInterval), e rimontato (nuovo setInterval) a ogni tick del timer. Il timer sembrava funzionare ma con un overhead costante di mount/unmount.

**Fix:** Rimosso `seconds` dall'array di dipendenze (`[isRunning]` sola). Nella branch `else` (stop), rimosso il guard `if (seconds > 0)` — superfluo perché `setSeconds(0)` quando il valore è già 0 non causa re-render in React.

```diff
-    }, [isRunning, seconds]);
+    }, [isRunning]);
```

### V2 — preload/index.ts: tipo `any` su config e _event
**File:** `src/preload/index.ts`

**Problema:** `startStream: (config: any)` accettava qualsiasi oggetto senza type checking. `_event: any` nascondeva il tipo Electron corretto.

**Fix:** Definita interface `StreamConfig` locale al file preload (include `inputDeviceName` che viene aggiunto in `App.tsx` prima dell'invio). Sostituito `any` con `IpcRendererEvent` importato da electron.

```diff
-import { contextBridge, ipcRenderer } from 'electron';
+import { contextBridge, ipcRenderer, IpcRendererEvent } from 'electron';
+
+interface StreamConfig { ... }
+
-    startStream: (config: any) => ...
+    startStream: (config: StreamConfig) => ...
-    const handler = (_event: any, ...) => ...
+    const handler = (_event: IpcRendererEvent, ...) => ...
```

**Nota:** Il tipo `targetDeviceId: any` in `useAudioVisualizer.ts` era già stato corretto nella v0.3.0 (`{ exact: string } | undefined`). Confermato corretto.

### V3 — useStore.ts: password in chiaro nel localStorage
**File:** `src/renderer/store/useStore.ts`

**Problema (sicurezza):** `partialize` persisteva l'intero `streamConfig` inclusa la `password`. Il localStorage del browser Electron è accessibile in plaintext dal filesystem: `%APPDATA%/Runtime StreamFlow/Local Storage/`. Chiunque accedesse al PC poteva leggere la password Icecast/AzuraCast.

**Fix:** Riscritta `partialize` per costruire esplicitamente l'oggetto da persistere, escludendo `password`. Per mantenere la conformità TypeScript con `StreamConfig` (che richiede `password: string`), il campo viene serializzato come stringa vuota — viene ripristinato a `''` al caricamento, obbligando il re-insert manuale ad ogni sessione.

```diff
 partialize: (state) => ({
     selectedDeviceId: ...,
     selectedDeviceLabel: ...,
-    streamConfig: state.streamConfig
+    streamConfig: {
+        host: state.streamConfig.host,
+        port: state.streamConfig.port,
+        mount: state.streamConfig.mount,
+        icecastUser: state.streamConfig.icecastUser,
+        password: '', // never persisted to localStorage
+    },
 }),
```

### V4 — main.ts: doppia registrazione ipcMain su macOS `activate`
**File:** `src/main/main.ts`

**Problema:** L'evento `app.on('activate')` su macOS ri-chiama `createWindow()` e `initializeIpc()`. La seconda chiamata a `initializeIpc()` registrava di nuovo tutti gli handler `ipcMain.handle()` già registrati, causando warning Electron `"Attempted to register a second handler for..."` e potenzialmente comportamento indefinito su Mac.

**Fix:** Introdotta variabile modulo `let ipcInitialized = false`. `initializeIpc()` viene chiamata solo se `!ipcInitialized`, e il flag viene impostato a `true` alla prima registrazione.

```diff
+let ipcInitialized = false;
 
 app.whenReady().then(() => {
     createWindow();
     if (mainWindow) {
         initializeIpc(mainWindow);
+        ipcInitialized = true;
     }
     app.on('activate', () => {
         if (BrowserWindow.getAllWindows().length === 0) {
             createWindow();
-            if (mainWindow) {
+            if (mainWindow && !ipcInitialized) {
                 initializeIpc(mainWindow);
+                ipcInitialized = true;
             }
         }
     });
 });
```
