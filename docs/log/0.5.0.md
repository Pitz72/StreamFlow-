## Sessione di test AzuraCast — 2026-05-17 (post-release)

### Bug trovati e corretti durante i test

**BUG-T1 — variabile `logUrl` inutilizzata in `ffmpeg-manager.ts`** *(corretto)*  
TypeScript strict bloccava la build. Rimossa la variabile dichiarata ma mai usata.

**BUG-T2 — Mount point sbagliato dal Wizard AzuraCast** *(corretto)*  
`fetchStationDetail` estraeva il mount dalla `listen_url` proxiata:
`/listen/runtime_la_radio_geek/radio.mp3` → errato.
Il mount Icecast corretto è in `mounts[is_default].path` = `/radio.mp3`.
Fix: uso di `station.mounts` invece di `station.listen_url` per ricavare il mount.
La porta viene ora sempre impostata a `'8000'` (default Icecast source), non derivata dall'URL HTTPS.

**BUG-T3 — Encoding username nell'URL FFmpeg** *(corretto)*  
Il username `pizzisimone1972@gmail.com` veniva url-encodato come `%40` nell'URL FFmpeg.
Non è garantito che FFmpeg decodifichi `%40` prima di costruire l'header `Authorization: Basic`.
Fix: credenziali spostate fuori dall'URL e passate via header esplicito:
`Authorization: Basic base64(user:password)` in `-headers`.

**BUG-T4 — Error reporting poco leggibile** *(corretto)*  
Le ultime 3 righe di stderr FFmpeg erano sempre cleanup noise (`Error muxing`, `Error writing trailer`, `-10053`).
Fix: il log cerca prima una riga contenente pattern HTTP riconoscibili (`40x`, `Connection refused`, `Unauthorized`, ecc.).
Se trovata, mostra quella; altrimenti fallback sulle ultime 3 righe.

### BUG NON RISOLTO — Streaming verso AzuraCast/Liquidsoap (da riprendere)

**Sintomo:** Errore `-10053 WSAECONNABORTED` dopo "Error muxing a packet".

**Analisi:**
- Porta 8000 raggiungibile ✓ (`Server: Icecast 2.4.0-kh22`)
- PUT `/radio.mp3` con credenziali errate → `401 Authentication Required` ✓ (server risponde correttamente)
- PUT `/radio.mp3` con credenziali corrette → connessione accettata, FFmpeg avvia muxing, poi -10053

**Root cause identificato:**  
Dallo stato Icecast (`/status-json.xsl`): **Liquidsoap è connesso come sorgente permanente a `/radio.mp3` da giorni** (`connected: 268910s`, `stream_start: 14/May/2026`). Icecast accetta la PUT di StreamFlow (autenticazione OK), poi chiude la connessione perché il mount è già occupato da Liquidsoap.

In AzuraCast con backend Liquidsoap, il DJ **non si connette a Icecast direttamente**. Si connette all'**input harbor di Liquidsoap**, che ascolta su una porta separata. Liquidsoap gestisce lo switch automation→live e continua a pushare su Icecast.

**Cosa manca per risolvere:**
1. Trovare la porta harbor di Liquidsoap nella configurazione AzuraCast (probabilmente 8005 o altra porta configurabile).
2. Verificare se il protocollo sul harbor è identico (HTTP PUT Icecast) o se richiede qualcosa di diverso.
3. Aggiornare `fetchStationDetail` per recuperare la porta harbor dall'API AzuraCast (se esposta).
4. Alternativa: verificare se AzuraCast espone la porta DJ via API (`/api/station/{id}` o endpoint dedicato).

**Prossima sessione:** investigare con Opus.
