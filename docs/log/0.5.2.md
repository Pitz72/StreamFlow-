# Log tecnico — v0.5.2

**Data:** 2026-05-17
**Tipo:** Quick fixes post-release (Now Playing, volume input)
**Contesto:** Prima sessione di streaming live AzuraCast riuscita dopo il fix harbor di v0.5.1. L'utente ha individuato durante l'uso tre criticità a basso/medio sforzo, che sono state risolte in questa iterazione.

---

## Issue affrontate

### 1. Now Playing aveva 3 campi invece di 2

**Sintomo:** UI mostrava Show, Artist, Title. AzuraCast (e ogni altro display Icecast) ne visualizza sempre 2.
**Causa:** Il protocollo Icecast `updinfo` invia un solo parametro `song`, formato per convenzione come `"Artist - Title"`. Il campo Show era un'invenzione concettuale nostra che riempiva l'`artist` come fallback se l'`artist` era vuoto, ma non veniva mai trasmesso come voce separata.
**Fix:** Rimosso `showName` da `StreamMetadata` interface, da `NowPlayingPanel` UI, dal fallback in `App.tsx → onStreamStatus`. Conservato il commento nel JSX che spiega il vincolo del protocollo.

### 2. Now Playing dichiarava "✓ Inviato" anche quando il server rifiutava i metadati

**Sintomo:** Toast verde "✓ Inviato alle HH:MM" ma AzuraCast non aggiornava la riga Now Playing.
**Causa:** `MetadataManager.send()` considerava successo qualsiasi risposta con `statusCode < 400`. Il harbor Liquidsoap (porta 8005, dove ora puntiamo per lo streaming dopo v0.5.1) non implementa `/admin/metadata`: restituisce 200 con una pagina HTML di default o body vuoto, e il nostro client lo interpretava come "tutto ok".
**Fix:** Validazione vera della risposta in `metadata-manager.ts`:
- HTTP >= 400 → rigetta con body del server (primi 150 char)
- Body che inizia con `<!doctype` o `<html` → rigetta con messaggio esplicito "Server non Icecast — i metadati non verranno applicati"
- XML Icecast con `<return>0</return>` → estrae `<message>` ed esegue reject
- Logga su console main process: `[MetadataManager] host:port/path → HTTP X, body[0..200]="..."` per debug

Inoltre: encoding del mount corretto. Prima usavamo `encodeURIComponent(mount)` che trasforma `/` in `%2F` — alcuni harbor sono strict sul match. Ora il `/` rimane letterale, l'encoding si applica solo ai segmenti interni del path.

UI: il toast errore in `NowPlayingPanel` ora mostra l'`error` reale restituito dall'IPC invece del generico "server raggiungibile?". Timeout esteso a 8s per dare tempo di leggere.

**Stato funzionale:** Il fix rende ONESTO il feedback ma NON garantisce che i metadati arrivino effettivamente ad AzuraCast — il problema sottostante è che Liquidsoap harbor (così come configurato in questa AzuraCast install) non sembra supportare l'aggiornamento metadata. Possibili soluzioni future:
- Inviare i metadata a Icecast (`host:8000` + mount listener) anziché al harbor — richiede di tenere traccia di due endpoint
- Usare un'API AzuraCast dedicata (da verificare se esiste un endpoint pubblico per DJ live)
- Inviare metadata in-stream tramite Icy-Title header in FFmpeg

Da riprendere in una sessione successiva.

### 3. Volume input — Fase D1

Slider nuovo in Configurazione, sotto Bitrate. Range 0–200%, step 5, default 100%.
- Campo `inputGain: string` aggiunto a `StreamConfig` nello store, persistito in localStorage.
- Aggiunto anche a `ServerProfile` (con default fallback `'100'` su `loadProfile` per profili pre-v0.5.2).
- `ffmpeg-manager.ts` inserisce `-af volume=X` nella pipeline solo se `gainPct !== 100`, per evitare overhead di filtraggio al default.
- Conversione percentuale → moltiplicatore: `parseInt(inputGain) / 100`, clamp a [0, 200]. Es. `150%` → `volume=1.50`.
- Log diagnostico aggiornato: `[StreamManager] Connecting → host:port/mount as user="X" gain=Y%`.
- UI: slider con accent blue, labels 0/100/200 sotto, valore corrente a destra in monospace. Nota "Modifica applicata al prossimo avvio dello stream" perché FFmpeg non ricarica i filtri dinamicamente — il valore corrente si fissa allo `spawn`.

- **Build NSIS**: l'utente ha richiesto esplicitamente di skippare il build in questa iterazione.
- **Risoluzione effettiva metadata su AzuraCast/Liquidsoap**: come spiegato sopra, il fix corrente garantisce solo feedback onesto. Per fare arrivare i metadata serve un'iterazione dedicata con accesso al server (per verificare cosa risponde l'harbor) o un endpoint AzuraCast alternativo.
