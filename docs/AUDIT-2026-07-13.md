## Scopo del software (verificato sul codice)

StreamFlow è un client desktop Electron per streaming audio live verso server Icecast/Shoutcast e AzuraCast (DJ Mode / harbor Liquidsoap). Cattura l'audio da un dispositivo Windows (DirectShow), lo encoda in MP3 con FFmpeg e lo trasmette via HTTP PUT. Funzionalità: VU meter, timer di sessione, invio metadata "Now Playing" (updinfo via raw socket BUTT-compatibile), wizard di auto-configurazione AzuraCast, profili server, log eventi a video, controllo volume input.

Architettura a 3 processi: **Main** (lifecycle, FFmpeg, socket metadata, API AzuraCast) ↔ **Preload** (contextBridge, corretto: contextIsolation on, nodeIntegration off) ↔ **Renderer** (React 19 + Zustand + Tailwind).

Il nucleo funziona (confermato dai test live documentati), ma la gestione del ciclo di vita del processo FFmpeg contiene race condition reali che possono produrre **stream orfani non stoppabili**, **doppio stream simultaneo** e **stato UI incoerente**. A questo si sommano l'assenza di auto-reconnect (già nota) e un bug sul volume 0%.

## 🔴 GRAVISSIME

### G1 — Race condition stop→start: il close handler del vecchio FFmpeg azzera il riferimento al nuovo processo

**File:** [ffmpeg-manager.ts:189-191](../src/main/streaming/ffmpeg-manager.ts) e [ffmpeg-manager.ts:239-254](../src/main/streaming/ffmpeg-manager.ts)

`stop()` lancia `taskkill` **asincrono** (fire-and-forget) e imposta subito `this.ffmpegProcess = null`, ma **non stacca i listener** del processo morente. Il suo evento `close` arriva dopo, e il handler esegue **incondizionatamente**:

```ts
this.ffmpegProcess.on('close', (code) => {
    cancelConnectionTimeout();
    this.ffmpegProcess = null;   // ← azzera QUALUNQUE cosa ci sia, anche il processo NUOVO
    if (code !== 0 && code !== null) { ... sendStatus('error') ... }
```

**Scenario di fallimento concreto (stop → start rapido, o doppio avvio):**
1. Stream attivo. L'utente ferma e riavvia.
2. `stop()`: taskkill parte in background, `ffmpegProcess = null`, status `disconnected`.
3. `start()`: spawna il **nuovo** FFmpeg, `this.ffmpegProcess = nuovoProcesso`.
4. Il **vecchio** processo muore (taskkill completa) → il suo `close` scatta con code=1 → `this.ffmpegProcess = null` **cancella il riferimento al nuovo processo** e manda `sendStatus('error')`.
5. Risultato: la UI mostra "Error" e `isStreaming=false` mentre il nuovo FFmpeg **sta realmente trasmettendo**; un successivo "stop" non ha nulla da killare (`ffmpegProcess` è null) → **stream orfano che continua ad andare in onda, fermabile solo da Task Manager**. Un nuovo "GO" spawna un terzo FFmpeg → **due sorgenti contemporanee sullo stesso harbor**.

**Fix:** catturare il processo in una variabile locale nel `start()` e nei handler verificare `if (this.ffmpegProcess !== proc) return;` (oppure `removeAllListeners()` in `stop()` prima del kill + flag `stoppedByUser`).

### G2 — Ogni stop manuale genera uno stato "error" spurio

**File:** [ffmpeg-manager.ts:189-219](../src/main/streaming/ffmpeg-manager.ts), [ffmpeg-manager.ts:244](../src/main/streaming/ffmpeg-manager.ts)

`taskkill /f` termina FFmpeg con **exit code 1**. Il handler `close` tratta ogni `code !== 0 && code !== null` come crash: dopo il `disconnected` inviato da `stop()`, arriva un secondo status `error` con toast ("FFmpeg: … | Exiting normally… | ecc."). Non esiste alcun flag "stop richiesto dall'utente". Oltre al rumore UX, questo scrive nel log un `✗` errore a ogni chiusura regolare e — combinato con G1 — corrompe lo stato.

**Fix:** flag `intentionalStop` impostato in `stop()` e verificato nel close handler (è lo stesso punto dove andrà l'auto-reconnect, vedi G3).

---

### G3 — Nessun auto-reconnect: caduta dello stream = silenzio in onda finché non si interviene a mano

**File:** [ffmpeg-manager.ts:189](../src/main/streaming/ffmpeg-manager.ts) (handler `close`) — issue già nota (roadmap Fase C1, confermata da test: stream caduto dopo alcune ore).

Per un tool di broadcasting è la criticità operativa massima: una disconnessione TCP transitoria (rete, NAT timeout, riciclo sessione harbor) termina FFmpeg e l'app resta in `error` senza alcun retry. **Fix pianificato e corretto:** backoff 5s→10s→30s→60s→120s, max 5 tentativi, countdown in UI, eventi nel StreamLog. Va implementato **insieme** a G1/G2 perché tutti e tre vivono nello stesso handler `close` e richiedono la distinzione stop-volontario / crash.

## 🟠 GRAVI

### S1 — Volume input 0% viene silenziosamente convertito in 100%

**File:** [ffmpeg-manager.ts:111](../src/main/streaming/ffmpeg-manager.ts)

```ts
const gainPct = Math.max(0, Math.min(200, parseInt(inputGain || '100', 10) || 100));
```

`parseInt('0') === 0` è falsy → `0 || 100` → **100**. L'utente porta lo slider a 0 aspettandosi il mute e va in onda a **volume pieno**. Incidente on-air potenziale. Anche 1–4% funziona, solo lo 0 esatto è rotto.

**Fix:** `const parsed = parseInt(inputGain ?? '100', 10); const gainPct = Number.isFinite(parsed) ? Math.max(0, Math.min(200, parsed)) : 100;`

### S2 — Credenziali visibili nella command line di FFmpeg

**File:** [ffmpeg-manager.ts:105-131](../src/main/streaming/ffmpeg-manager.ts)

L'header `Authorization: Basic <base64(user:password)>` è passato come **argomento di riga di comando** a FFmpeg: qualunque processo/utente locale lo legge da Task Manager / `wmic process get commandline` / Process Explorer, e Base64 si decodifica banalmente. Limite noto dei client CLI (FFmpeg non legge headers da stdin), ma va almeno: (a) documentato come rischio accettato, (b) mitigato non loggando mai `args` e valutando `windowsHide: true` sullo spawn. Anche l'URL in chiaro `http://` espone la password in transito sulla rete (Icecast source su TLS è spesso non disponibile — rischio da documentare).

### S3 — Crash non gestito alla chiusura dell'app mentre si è ON AIR

**File:** [ffmpeg-manager.ts:81-85](../src/main/streaming/ffmpeg-manager.ts), [main.ts:26-28,61-63](../src/main/main.ts)

Flusso: X sulla finestra → `closed` (il `mainWindow` locale di main.ts va a null, ma **StreamManager tiene la sua copia**) → `window-all-closed` → `app.quit()` → `before-quit` → `cleanupIpc()` → `stop()` → `sendStatus('disconnected')` → `this.mainWindow.webContents.send(...)` su finestra **distrutta** → `TypeError: Object has been destroyed` non catturata nel main process. Il taskkill è già partito quindi FFmpeg muore comunque, ma `metadataManager.clearConfig()` non viene eseguito e l'eccezione sporca la chiusura.

**Fix:** in `sendStatus` (e ovunque si tocchi `webContents`): `if (this.mainWindow && !this.mainWindow.isDestroyed())` + try/catch (come già fatto per `emitLog` in ipcp.ts:20-24 — l'incoerenza tra i due punti è il bug).

### S4 — Su macOS la riapertura da dock produce una finestra "morta"

**File:** [main.ts:42-50](../src/main/main.ts)

Nell'handler `activate`, `createWindow()` ricrea la finestra ma `ipcInitialized` è già `true`, quindi non viene mai richiamato `initializeIpc`: il nuovo `BrowserWindow` non è collegato a StreamManager (`setMainWindow` esiste ma non è mai usato), a `emitLog` (closure sulla finestra vecchia distrutta) né al `did-finish-load`. Risultato: status, log e stato stream non arrivano più alla UI. Target primario è Windows, ma il codice del percorso macOS è oggettivamente rotto; inoltre se `initializeIpc` venisse richiamato, `ipcMain.handle` duplicati farebbero throw ("second handler"). Da sistemare separando "registrazione handler IPC" (una volta) da "aggancio finestra" (a ogni finestra).

### S5 — Doppio click su GO nel varco pre-"connecting"

**File:** [App.tsx:96-131](../src/renderer/App.tsx), [OnAirButton](../src/renderer/components/OnAirButton.tsx)

Il bottone si disabilita solo quando lo status `connecting` **torna indietro** dal main via IPC. Tra il primo click e quell'evento c'è una finestra (decine di ms, di più se il main è occupato) in cui un secondo click invoca `startStream` di nuovo → due `start()` in sequenza → si innesca esattamente la race G1 (il secondo `start()` killa il primo processo il cui `close` azzererà il riferimento al secondo). **Fix:** guard sincrono nel renderer (`useRef` "startInFlight") e/o guard nel main (`if (starting) return`).

## 🟡 MEDIE

### M1 — I VU meter "L" e "R" sono identici (falso stereo) e duplicano l'intera pipeline audio

**File:** [VuMeter.tsx:9-11](../src/renderer/components/VuMeter.tsx), [useAudioVisualizer.ts](../src/renderer/hooks/useAudioVisualizer.ts)

Ogni `<VuMeter>` chiama `useAudioVisualizer(selectedDeviceId)`: **due** AudioContext + **due** getUserMedia + due AnalyserNode sullo stesso device, ed entrambi calcolano la **media mono** dell'intero spettro. "L" e "R" mostrano lo stesso valore: il claim documentale "VU stereo L/R indipendenti" non corrisponde al codice. Fix: un solo context condiviso + `ChannelSplitterNode` per i canali reali (o dichiarare il meter mono).

### M2 — Il microfono resta acquisito sempre, anche off-air

**File:** [useAudioVisualizer.ts:31,49](../src/renderer/hooks/useAudioVisualizer.ts)

Il visualizer apre `getUserMedia` al mount e lo tiene aperto per tutta la vita dell'app (indicatore privacy OS sempre acceso, device lock, consumo). Scelta forse voluta (preview pre-live), ma andrebbe legata a uno stato (es. attivo solo con finestra a fuoco o con toggle).

### M3 — Header/CRLF injection nei metadata inviati via raw socket

**File:** [metadata-manager.ts:50-52,71-79](../src/main/streaming/metadata-manager.ts)

`buttEncode` codifica solo spazio e `&`. Artist/title contenenti `\r`/`\n` (incolla da clipboard!) finiscono **letterali dentro la richiesta HTTP scritta a mano**, spezzandola o iniettando header. Anche `?`, `#`, `%` alterano l'URL. Fix minimo: `s.replace(/[\r\n]/g, ' ')` prima dell'encode; meglio estendere l'encode a tutti i byte problematici tranne quelli che Liquidsoap richiede letterali.

### M4 — CSP debole: `unsafe-inline` + `unsafe-eval` in produzione

**File:** [index.html:8-9](../src/renderer/index.html)

`script-src 'self' 'unsafe-inline' 'unsafe-eval'` vanifica gran parte della CSP in un'app Electron. Il build Vite di produzione non richiede né eval né inline scripts. Fix: `script-src 'self'` (eventualmente CSP diversa solo in dev per HMR).

### M5 — `sandbox: false` non necessario

**File:** [main.ts:15](../src/main/main.ts)

Il commento dice "For FFmpeg spawning", ma FFmpeg è spawnato nel **main process**, non nel preload: il sandbox del renderer non c'entra. Con `contextIsolation: true` e il preload attuale (solo ipcRenderer), `sandbox: true` funziona e riduce la superficie d'attacco. Manca anche la guardia di navigazione (`setWindowOpenHandler` / `will-navigate`) raccomandata dalle checklist Electron.

### M6 — `exec(taskkill)` mai atteso: possibile FFmpeg orfano proprio alla chiusura dell'app

**File:** [ffmpeg-manager.ts:244](../src/main/streaming/ffmpeg-manager.ts), [main.ts:61-63](../src/main/main.ts)

In `before-quit`, `stop()` lancia `exec` e ritorna subito; l'app può terminare prima che `taskkill` sia stato eseguito. Fix: usare `execSync`/`spawnSync` nel solo percorso di quit, oppure `event.preventDefault()` + await + `app.exit()`.

### M7 — API AzuraCast: i redirect HTTP non vengono seguiti

**File:** [azuracast-api.ts:41-67](../src/main/azuracast/azuracast-api.ts)

`http/https.request` nativo non segue 301/302. Un utente che digita `http://radio.example.com` (redirect a https, configurazione comunissima) riceve l'errore opaco "HTTP 301". Fix: seguire manualmente `location` (1-2 hop) o almeno messaggio esplicito "usa https://". Nota collegata: se l'utente usa `http://`, l'**API key viaggia in chiaro**.

### M8 — `handleSend` senza try/catch: UI bloccata su "sending" per sempre

**File:** [NowPlayingPanel.tsx:12-34](../src/renderer/components/NowPlayingPanel.tsx)

Se `updateMetadata` rigetta (es. eccezione sincrona nel main — `sock.connect(NaN)` con porta corrotta — o canale IPC in errore), la promise rifiuta, nessuno la cattura, `sendStatus` resta `'sending'` e il bottone resta disabilitato fino alla riapertura del modale. Stesso pattern in [AzuraCastWizard.tsx:53,68](../src/renderer/components/AzuraCastWizard.tsx) (stato stuck su "loading"). Fix: try/catch/finally attorno alle await.

### M9 — Nessun single-instance lock

**File:** [main.ts](../src/main/main.ts)

`app.requestSingleInstanceLock()` assente: due istanze di StreamFlow possono partire, contendersi il device dshow e connettersi entrambe all'harbor (che butta fuori la prima). Tre righe di fix standard.
